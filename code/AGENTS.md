# Codex 单文件开发流程

> 使用方法：把本文件复制到任意项目根目录并命名为 `AGENTS.md`。Codex 读取本文件后，必须先根据用户当前任务生成具体开发文档，再等待确认或按照已确认计划一步一步开发、测试和验收。

## 1. 核心目标

所有需要新增、修改或删除代码的任务，都必须遵循：

```text
理解用户任务
→ 只读检查真实项目
→ 展示 Updated Plan
→ 生成具体任务开发文档
→ 确认计划
→ 一次执行一个步骤
→ 每步完成后验证
→ 完整测试和构建
→ 最终验收和总结
```

禁止未规划直接写代码，也禁止写完代码后再补计划。

## 2. 单文件自动生成规则

本 `AGENTS.md` 是唯一需要迁移的流程文件，不依赖其他模板。

接到开发任务后，Codex 应根据本文件内置结构自动创建：

```text
开发任务/<任务编号>-<任务简称>.md
```

示例：

```text
开发任务/TASK-001-用户登录.md
开发任务/BUG-002-修复导出失败.md
```

生成的任务文档必须包含：

1. 任务目标和范围；
2. 真实项目与代码分析；
3. 具体修改方案；
4. 分步实施计划；
5. 测试用例；
6. 验收标准；
7. 实施和验证记录；
8. 最终验收结论。

任务文档必须根据用户要求和真实代码生成，不得只是复制空模板。

## 3. 写代码前的强制流程

### 3.1 阅读项目规则

依次检查：

1. 用户当前要求；
2. 当前 `AGENTS.md`；
3. 子目录中适用的其他 `AGENTS.md`；
4. 项目 README 和开发说明；
5. 构建、测试、依赖和 CI 配置；
6. 当前工作区已有修改。

### 3.2 只读分析

第一次修改业务文件前，至少确认：

- 项目技术栈；
- 应用和业务入口；
- 与任务相关的调用关系；
- 可以复用的组件、服务和工具；
- 已有测试及测试框架；
- 实际构建和测试命令；
- 预计修改文件；
- 用户已有且必须保留的修改；
- 风险、依赖和待确认问题。

禁止根据经验虚构文件路径、接口、命令或实现方式。

### 3.3 展示 Updated Plan

在第一次写文件之前，必须使用 Codex 计划功能展示可见的 `Updated Plan`。

普通任务拆分为 3～7 步，小型任务可以使用 2～4 步。例如：

```text
Updated Plan
├── 检查需求、代码入口和现有测试
├── 生成具体任务开发文档
├── 实现核心修改
├── 补充或更新测试
└── 运行测试、构建并检查最终差异
```

状态规则：

- `pending`：尚未开始；
- `in_progress`：当前正在执行；
- `completed`：已经执行并完成验证。

同一时间只能有一个步骤处于 `in_progress`。

### 3.4 生成具体任务文档

完成只读分析后，按照第 8 节的结构生成本次任务文档。

任务文档初始状态必须为：

```text
待确认
```

如果用户只要求规划，生成任务文档后停止，不修改业务代码。

如果用户尚未明确批准实施，生成后向用户汇报计划并等待确认。

如果用户已经明确要求按照计划直接实施，可以在没有阻塞问题的情况下继续，但仍必须先生成任务文档和可见计划。

存在以下情况时必须先确认：

- 关键需求存在歧义；
- 需要扩大用户要求的范围；
- 需要修改公共接口或破坏兼容性；
- 需要数据库迁移、数据删除或不可逆操作；
- 需要升级或新增重要依赖；
- 需要修改部署、生产或安全配置；
- 发现与用户已有修改冲突。

## 4. 分步骤开发规则

计划确认后严格按照任务文档执行：

1. 将当前步骤标记为 `in_progress`，其他步骤保持 `pending`。
2. 只修改当前步骤明确允许的文件。
3. 优先使用最小修改并复用现有能力。
4. 不进行无关重构、全局格式化或依赖升级。
5. 不修改自动生成文件和构建输出。
6. 不删除、覆盖或回退用户已有修改。
7. 不提前实施后续步骤。
8. 完成当前步骤后执行对应验证。
9. 验证完成后，将步骤标记为 `completed`。
10. 同步更新任务文档的实施记录。
11. 再将下一步骤标记为 `in_progress`。

不得一次性把多个尚未执行或尚未验证的步骤标记为完成。

实现过程中发现范围、方案、风险或依赖变化时，先更新任务文档和 `Updated Plan`，再继续开发。

## 5. 测试规则

测试命令必须从项目真实配置中确认，来源包括：

- README；
- 包管理配置；
- 构建配置；
- CI 配置；
- 项目脚本；
- 已有测试目录。

不得凭空编造测试命令。

测试根据项目能力依次考虑：

1. 语法、格式或类型检查；
2. 相关单元测试；
3. 相关集成测试；
4. 异常和边界测试；
5. 受影响模块回归测试；
6. 项目构建；
7. 必要的完整测试或手工验证。

每次验证必须记录：

- 实际命令或操作；
- 退出状态；
- 通过或失败结果；
- 失败原因；
- 未执行内容及原因。

未执行的检查必须标记为 `未执行`，不得标记为通过。

禁止通过删除测试、降低断言、忽略错误或关闭检查使验证通过。

## 6. 验收规则

完成代码和测试后，必须检查：

- 用户目标是否实现；
- 需求和验收标准是否满足；
- 正常、异常和边界场景是否验证；
- 测试及构建是否成功；
- 是否存在范围外修改；
- 是否破坏接口、数据或配置兼容性；
- 是否存在安全或数据风险；
- 是否遗留调试代码、临时文件或敏感信息；
- 任务文档是否与实际实现一致。

验收结论只能是：

- `通过`；
- `有条件通过`；
- `不通过`；
- `阻塞`。

代码已经编写不等于验收通过。

## 7. 最终回复规则

任务结束时向用户报告：

1. 实现内容；
2. 修改文件；
3. 执行的测试和构建命令；
4. 实际验证结果；
5. 未执行的验证及原因；
6. 已知问题和残余风险；
7. 验收结论；
8. 建议的下一步。

最终回复必须基于真实执行结果，不得把推测写成事实。

## 9. 简单使用方式

将本文件复制到目标项目根目录后，对 Codex 说：

```text
请根据 AGENTS.md，先分析当前项目，为下面的任务生成具体任务开发文档，暂时不要写业务代码：

<在这里描述任务>
```

确认计划后说：

```text
计划确认，按照任务开发文档和 Updated Plan 一步一步实施。每完成一步先验证并更新状态，再开始下一步。
```
