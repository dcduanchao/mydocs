# 微服务与分布式事务

## 1. 微服务解决什么问题

微服务把大型系统按业务能力拆成可独立开发、部署和扩缩容的服务。它主要解决团队协作、发布边界、故障隔离和不同业务容量差异，不是为了“接口看起来更多”。

```text
单体应用
  -> 按领域边界拆分
  -> 独立服务、数据和发布流程
  -> 引入网络、最终一致性和运维复杂度
```

微服务的代价：

- 本地方法调用变成不可靠网络调用。
- 单库事务变成跨服务一致性问题。
- 日志、指标和调用链分散。
- 部署、配置、版本兼容和测试更复杂。
- 故障可能通过重试和依赖链级联扩散。

业务规模和团队规模不足时，模块化单体往往更合适。先建立清晰模块边界，再根据独立发布和容量需要拆服务。

## 术语速览

| 名称 | 含义 |
|---|---|
| Service Discovery | 服务实例注册与发现。 |
| API Gateway | 统一入口、路由和边缘治理。 |
| Circuit Breaker | 熔断器，在依赖持续失败时快速拒绝。 |
| Bulkhead | 舱壁隔离，为不同依赖分配独立资源。 |
| Idempotency | 同一请求重复执行，业务结果保持一致。 |
| Outbox | 业务数据与待发送事件在同一数据库事务落库。 |
| Saga | 多个本地事务组成的长事务，并通过补偿处理失败。 |
| TCC | Try、Confirm、Cancel 三阶段业务事务。 |
| XA/2PC | 协调多个资源进行准备和提交的两阶段提交。 |
| CDC | 捕获数据库变更并发布到下游。 |

## 2. 服务拆分

### 2.1 按业务能力拆分

```text
订单域：下单、订单状态
库存域：可售库存、预占与释放
支付域：支付单、退款
用户域：账号、身份与地址
```

边界应围绕领域职责和数据所有权，而不是按 Controller、Service、DAO 技术层拆分。

合理边界具有：

- 明确业务术语和职责。
- 大部分操作能在服务内部完成。
- 数据由一个服务负责写入。
- API 和事件契约稳定。
- 可以独立部署和容量规划。

两个服务持续双向同步调用、共享大量表、必须同时发布，通常说明边界不合理。

### 2.2 Database per Service

每个服务拥有自己的数据，其他服务通过 API 或事件访问。即使早期共用 MySQL 实例，也应按 Schema、账号和写权限隔离。

禁止服务 A 直接更新服务 B 的表。跨库 Join 应通过：

- API 组合。
- 搜索/查询侧物化视图。
- 数据仓库或报表平台。
- 事件同步后的本地冗余数据。

数据冗余是微服务常见做法，但必须明确事实数据源、同步延迟和重建流程。

## 3. 同步与异步通信

| 方式 | 优点 | 风险 |
|---|---|---|
| HTTP/RPC | 调用简单、立即得到结果 | 时延耦合、级联故障 |
| 消息队列 | 解耦、削峰、可重试 | 最终一致、重复和乱序 |
| 事件流 | 可回放、多消费者 | 契约演进和存储治理复杂 |

同步调用适合调用方必须立即得到结果的查询或命令；异步事件适合通知、状态传播和可延迟处理。不要把所有通信都改成消息，也不要用层层同步调用构造分布式单体。

### 3.1 API 契约

- URL、字段和错误码保持向后兼容。
- 新增字段通常比删除或改变语义安全。
- Consumer 不应依赖未声明字段和列表顺序。
- 分页、时间、金额和枚举格式统一。
- 使用 OpenAPI、Protobuf 或 Schema Registry 管理契约。
- 破坏性变更通过新版本和迁移窗口完成。

## 4. 服务发现、配置与网关

### 4.1 服务发现

服务实例启动后注册地址并发送心跳，客户端或网关从注册中心获取健康实例列表。Kubernetes 场景通常使用 Service 和 DNS；其他环境可使用 Nacos、Consul 等。

注册中心健康不代表业务依赖全部健康。实例是否接收流量应由 Readiness 控制，Liveness 不应因短暂数据库故障触发全体重启。

### 4.2 配置中心

- 配置按应用、环境和版本隔离。
- 密码与证书使用 Secret/KMS，不放普通配置中心明文。
- 动态配置有类型、范围、审批、审计和回滚。
- 不是所有参数都适合热更新，线程池和连接池变更需要验证生命周期。
- 配置中心不可用时明确使用本地快照、拒绝启动还是降级运行。

### 4.3 API Gateway

网关适合统一处理：

- TLS 终止、路由和灰度。
- 认证、基础授权和限流。
- 请求大小、Header 和协议约束。
- Trace ID、访问日志和边缘指标。

网关不应承载复杂业务编排，也不能替代下游服务的数据权限。外部传入的身份 Header 必须清理，由可信网关重新生成并签名或通过 Token 传递。

## 5. 超时与 Deadline

任何远程调用都必须有连接超时、读取超时和总体 Deadline。

```text
入口剩余 2 秒
  -> 服务 A 处理 200 ms
  -> 调用 B 最多 1.5 秒
  -> B 调用 C 最多 1 秒
```

下游超时不能大于上游剩余时间。层层固定 3 秒会让上游已经超时后，下游仍继续占用资源。

区分：

- Connection Timeout：建立连接等待时间。
- Read/Response Timeout：等待响应数据时间。
- Pool Acquire Timeout：等待连接池资源时间。
- Business Deadline：整个业务请求的最后完成时间。

客户端超时只表示“没有及时收到结果”，不代表服务端一定没有执行。写操作重试必须具备幂等性。

## 6. 重试、退避与熔断

### 6.1 重试

仅对短暂故障和幂等操作重试，例如连接重置、明确的 429/503。参数错误、权限失败和业务冲突通常不应重试。

```text
delay = min(base × 2^attempt, maxDelay) + randomJitter
```

原则：

- 次数有上限，并受总体 Deadline 限制。
- 使用指数退避和随机抖动，避免同时重试。
- 只在一个层次重试，防止调用链倍增。
- 记录重试原因、次数和最终结果。
- 消费消息通过重试 Topic/延迟队列处理，不进行无限热循环。

三层各重试 3 次，最坏可能让最下游承受 27 次调用。

### 6.2 熔断

```text
CLOSED：正常调用并统计结果
  -> 失败率达到阈值
OPEN：快速失败，不再调用下游
  -> 等待恢复窗口
HALF_OPEN：允许少量探测
  -> 成功则关闭，失败则重新打开
```

熔断保护调用方资源，不能修复下游。阈值应基于最小请求量、失败率、慢调用比例和窗口，并监控状态变化。

### 6.3 隔离与限流

- 不同依赖使用独立连接池、Semaphore 或线程池。
- 核心与非核心流量使用不同配额。
- 入口限流保护系统容量，内部限流保护具体资源。
- 队列必须有界，满时快速拒绝或降级。
- 虚拟线程降低等待成本，但仍需 Semaphore 限制数据库和下游并发。

## 7. 幂等设计

### 7.1 幂等键

客户端为一次业务操作生成稳定 Idempotency Key：

```http
POST /payments
Idempotency-Key: 01J...XYZ
```

服务端保存：

```text
(caller, operation, idempotency_key)
  -> request_hash
  -> processing/succeeded/failed
  -> response_reference
```

同一 Key、相同请求返回第一次结果；同一 Key、不同请求体应拒绝。并发首请求使用数据库 Unique Key 原子抢占，不能只做“先查询再插入”。

```sql
CREATE UNIQUE INDEX uk_payment_idempotency
ON payment_request(caller_id, idempotency_key);
```

### 7.2 消费幂等

```sql
START TRANSACTION;

INSERT INTO consumed_event(consumer, event_id, consumed_at)
VALUES (?, ?, NOW());

-- 业务更新
UPDATE orders SET status = ? WHERE id = ?;

COMMIT;
```

`(consumer, event_id)` 使用唯一约束。重复事件插入冲突后确认业务已处理，再提交消息 Offset。

如果只在 Redis 记录去重而业务写 MySQL，两者之间仍有原子性窗口。去重记录最好与业务数据落在同一本地事务，或让业务更新本身天然幂等。

## 8. 分布式一致性基础

### 8.1 CAP

网络分区发生时，分布式系统无法同时保证强一致可用响应和所有请求持续成功，必须在一致性与可用性之间做取舍。CAP 讨论的是分区存在时的选择，不是平时从 C、A、P 中随意选两个。

业务还要考虑 PACELC：没有分区时，一致性与延迟之间仍有权衡。

### 8.2 最终一致性

最终一致不是“不管一致性”，而是明确：

- 哪个系统是事实数据源。
- 正常同步延迟和最大容忍时间。
- 失败如何重试、告警和进入死信。
- 重复、乱序和并发更新如何处理。
- 如何核对差异并重新构建下游数据。

## 9. 本地消息表与 Transactional Outbox

业务数据和事件在同一数据库事务写入：

```sql
START TRANSACTION;

INSERT INTO orders(id, status, ...)
VALUES (?, 'CREATED', ...);

INSERT INTO outbox_event(
    event_id, aggregate_type, aggregate_id,
    event_type, payload, status, created_at)
VALUES (?, 'ORDER', ?, 'OrderCreated', ?, 'NEW', NOW());

COMMIT;
```

后台 Publisher 轮询未发送事件，或 CDC 订阅 Outbox 表并发送到消息队列。

```text
本地事务 -> 业务表 + Outbox
             -> Publisher/CDC -> Broker
                                  -> Consumer 幂等处理
```

Outbox 保证“业务提交必有待发送事件”，但 Broker 投递和状态更新之间仍可能重复，因此消费者必须幂等。

设计要点：

- Event ID 全局唯一。
- Payload 是稳定事件契约，不直接序列化 Entity。
- Publisher 支持并发抢占、退避和故障恢复。
- 已发送事件按保留期归档或删除。
- 监控最老未发送事件年龄，而不只监控数量。
- 失败超过阈值进入人工可查的死信状态。

## 10. 可靠消息与事务消息

部分消息中间件提供事务消息：先发送半消息，执行本地事务，再提交或回滚消息；Broker 状态不明确时回查生产者。

```text
发送半消息 -> 执行本地事务 -> Commit 消息
                    |
                    -> 状态不明时 Broker 回查
```

回查逻辑必须能够根据事务 ID 从数据库确定状态。事务消息减少自行轮询 Outbox 的工作，但仍需处理重复消费、消息积压、回查压力和 Broker 依赖。

“消息已成功发送”不代表消费者业务已完成。端到端一致性仍依赖消费者幂等、重试和补偿。

## 11. Saga

Saga 把长事务拆成多个本地事务，每一步成功后执行下一步；后续失败时按相反顺序执行补偿。

```text
创建订单 -> 预占库存 -> 创建支付
                 失败
取消订单 <- 释放库存
```

两种协调方式：

- Choreography：服务通过事件自行响应，耦合低，但流程难以整体观察。
- Orchestration：协调器明确发出命令和记录状态，流程清晰，但协调器成为关键组件。

补偿不等于数据库回滚。例如退款可能产生手续费，取消发货可能已经无法执行。每个步骤需要设计业务可接受的补偿、重试、超时和人工介入状态。

Saga 状态机应持久化，并能从任意步骤恢复。事件乱序时使用状态版本或合法状态迁移校验。

## 12. TCC

```text
Try：检查并预留资源
Confirm：确认使用资源
Cancel：释放预留资源
```

库存示例：

```text
Try：available -= n，reserved += n
Confirm：reserved -= n，sold += n
Cancel：reserved -= n，available += n
```

TCC 对业务侵入较高，但能明确控制资源。必须处理：

- **空回滚**：Try 未执行成功，Cancel 先到，Cancel 也要成功记录。
- **悬挂**：Cancel 已执行后，迟到的 Try 不能再预留资源。
- **幂等**：Confirm/Cancel 重复调用结果一致。
- **并发隔离**：预留资源不能被其他事务使用。

使用全局事务 ID 和 Branch 状态唯一约束实现防重与状态机，而不是只依赖内存锁。

## 13. XA/2PC

两阶段提交：

```text
Phase 1 Prepare：所有参与者准备并锁定资源
Phase 2 Commit/Rollback：协调器决定统一提交或回滚
```

优点是提供较强原子提交语义；缺点是参与者长时间持有资源、协调器和恢复复杂、吞吐与可用性下降。适合参与资源少、事务短、基础设施明确支持且强一致要求高的场景。

不能为了避免业务补偿就默认选择 XA。跨公网、长流程和高并发业务通常更适合 Outbox/Saga。

## 14. Seata 模式边界

Seata 常见模式：

- AT：代理数据源，记录前后镜像并自动补偿，对 SQL 和数据库有约束。
- TCC：业务实现 Try/Confirm/Cancel。
- Saga：状态机和补偿事务。
- XA：使用数据库 XA 能力。

AT 模式并非零侵入魔法。上线前验证 SQL 支持、主键、全局锁、热点冲突、Undo Log、超时和回滚失败。高竞争资源可能因全局锁显著降低吞吐。

选择框架前先确定业务一致性目标和失败处理，再选择实现工具。

## 15. 分布式锁

分布式锁用于跨进程互斥，但不能替代数据库唯一约束、状态机和幂等。

风险：

- 锁租约过期后旧持有者仍继续执行。
- 网络超时无法确定加锁命令是否成功。
- 主从切换可能影响锁状态。
- 业务执行时间超过租约。
- 锁服务不可用导致业务不可用。

对需要防止旧持有者写入的资源使用 Fencing Token：每次获得锁取得单调递增 Token，下游只接受比已见 Token 更新的写入。

```text
Worker A token=10 -> 暂停
Worker B token=11 -> 写入成功
Worker A 恢复，以 token=10 写入 -> 下游拒绝
```

## 16. 顺序、重复与 Exactly Once

分布式系统中网络重试和故障恢复会产生重复。Broker 的 Exactly Once 能力通常只覆盖特定消息处理边界，无法自动保证“消息 + 数据库 + 外部支付”全链路仅执行一次。

工程目标通常是：

```text
At-least-once delivery + Idempotent consumer
  -> Effectively-once business effect
```

顺序通常只能在同一 Partition/Queue 内保证。需要按订单顺序时使用 `orderId` 作为分区键，并在消费者校验状态版本。全局顺序会限制并行能力，应避免不必要的要求。

## 17. 分布式 ID

常见方案：

| 方案 | 特点 |
|---|---|
| 数据库号段 | 趋势递增、批量取号，需要号段服务高可用。 |
| Snowflake | 本地生成、趋势递增，依赖机器 ID 和时钟。 |
| UUID v4 | 无中心、随机，索引局部性较差。 |
| UUID v7 | 带时间顺序，适合分布式且索引更友好。 |

Snowflake 必须处理时钟回拨和机器 ID 冲突。ID 只保证唯一，不代表安全；外部接口不能仅靠不可猜 ID 代替权限校验。

## 18. 可观测性

### 18.1 三大信号

- Logs：结构化事件和错误上下文。
- Metrics：QPS、错误率、延迟、饱和度和业务指标。
- Traces：一次请求跨服务的调用路径。

统一传播 W3C Trace Context，消息 Header 中也携带 Trace 上下文。异步事件还要记录 Event ID、Correlation ID 和 Causation ID。

### 18.2 SLI/SLO

不要只监控“服务是否存活”。为核心用户旅程定义：

- 成功率。
- P95/P99 延迟。
- 数据同步新鲜度。
- 消息最老积压时间。
- 一致性补偿未完成时间。

告警基于用户影响和错误预算，避免单个瞬时 CPU 峰值制造大量噪声。

## 19. 发布与故障演练

- 健康检查与优雅停机正确处理流量摘除。
- API 和事件先兼容旧消费者，再发布破坏性变更。
- 数据库使用 Expand/Contract：先加结构、双版本兼容、最后删除旧结构。
- 灰度观察错误率、延迟和业务指标，支持快速回滚。
- 定期演练节点宕机、网络延迟、Broker 不可用和配置错误。
- 故障注入有范围、终止条件和负责人，不在未知保护能力下直接全量执行。

## 20. 测试策略

- 单元测试：领域规则、幂等状态机和补偿逻辑。
- Contract Test：生产者与消费者 API/事件兼容。
- 集成测试：使用真实数据库、Broker、Redis 等容器。
- 端到端测试：覆盖关键用户旅程，不追求覆盖所有组合。
- 故障测试：超时、重复、乱序、部分成功和进程崩溃。
- 对账测试：验证全量核对、差异修复和事件重放。

只测试正常路径无法证明分布式流程可靠。至少在“每个网络调用返回前后崩溃”两个位置验证恢复行为。

## 21. 常见故障

### 21.1 重试风暴

症状是下游已经过载，上游多层立即重试进一步放大流量。应限制单层重试、指数退避、熔断、入口限流并保留重试预算。

### 21.2 消息积压

检查生产速率、消费耗时、错误重试、分区倾斜和下游容量。扩消费者前确认分区数和热点 Key；毒消息应进入死信而不是无限阻塞分区。

### 21.3 数据不一致

根据业务 ID 串联数据库记录、Outbox、Broker 和 Consumer 日志，确认事件是未生成、未发送、未消费还是消费失败。修复工具必须幂等、有审计并支持 Dry Run。

### 21.4 雪崩与级联故障

检查依赖拓扑、超时预算、线程/连接池等待、熔断和限流。增加线程数和队列可能只是积压更多请求，应先切断非核心流量并保护事实数据源。

## 22. 面试高频问题

### 22.1 微服务和单体如何选择

> 微服务适合业务边界明确、团队较多、独立发布和容量差异明显的系统，但会引入网络、最终一致性和运维成本。规模不足时优先模块化单体，边界成熟后再按需要拆分。

### 22.2 CAP 是什么

> 网络分区发生时，系统无法同时保证所有节点强一致响应和每个请求都可用，必须在一致性与可用性间选择。CAP 不是平时从三个字母任意选两个，分区容忍在分布式网络中通常无法回避。

### 22.3 如何保证接口幂等

> 客户端提供稳定幂等键，服务端使用数据库唯一约束原子记录请求状态和结果。同一 Key 相同请求返回首次结果，不同请求拒绝；处理中的并发请求等待或返回明确状态。不能只先查后插。

### 22.4 Outbox 如何保证一致性

> 业务数据和 Outbox 事件在同一本地事务提交，避免业务成功却没有待发送事件；Publisher 或 CDC 再发送到 Broker。发送和标记之间仍可能重复，所以消费者必须幂等，并监控未发送事件年龄。

### 22.5 Saga 和 TCC 有什么区别

> Saga 将多个已经提交的本地事务通过业务补偿串联，适合长流程；TCC 在 Try 阶段预留资源，再 Confirm 或 Cancel，控制更强但业务侵入更高，还要处理空回滚、悬挂和幂等。

### 22.6 为什么超时后不能直接重试写请求

> 客户端超时不代表服务端未执行，直接重试可能重复扣款或下单。写请求需要稳定业务号或幂等键，并在重试前查询或依赖服务端幂等状态。

### 22.7 熔断、限流和降级有什么区别

> 熔断针对依赖持续失败，暂时停止调用；限流把请求控制在系统容量内；降级在资源不足或依赖异常时返回简化结果或关闭非核心能力。三者目标不同，通常组合使用。

### 22.8 消息如何保证不丢

> 生产端使用 Outbox/事务消息和确认重试，Broker 配置复制与持久化，消费端处理成功后再提交位点，并通过幂等、死信和对账处理重复与失败。任一单点配置都不能独立保证端到端不丢。

### 22.9 什么是空回滚和悬挂

> TCC 中 Cancel 先于未成功的 Try 到达称为空回滚；Cancel 完成后迟到的 Try 又执行称为悬挂。分支事务表需要记录状态，使空 Cancel 幂等成功并拒绝迟到 Try。

### 22.10 分布式锁为什么需要 Fencing Token

> 租约过期后旧持有者可能继续执行，与新持有者并发写。Fencing Token 单调递增，下游拒绝旧 Token，即使旧进程恢复也不能覆盖新结果。

### 22.11 Exactly Once 是否真的存在

> 中间件可以在限定边界提供 Exactly Once，但跨数据库、消息和外部系统的端到端效果仍会遇到重试与部分失败。工程上通常用至少一次投递加幂等消费者，实现业务效果上的一次。

### 22.12 如何处理服务间循环依赖

> 重新检查领域边界，提取共同能力或使用领域事件解除同步调用。不能只靠增加超时和重试维持 A 调 B、B 又调 A 的结构，否则容易形成发布耦合和级联故障。

## 23. 生产环境检查清单

- [ ] 服务按领域和数据所有权拆分，不跨服务直接写表。
- [ ] 所有远程调用有连接、响应、资源等待超时和总体 Deadline。
- [ ] 重试有限、退避带抖动，并只作用于幂等临时故障。
- [ ] 核心依赖配置熔断、隔离、限流和有界队列。
- [ ] 写接口、消息消费和补偿操作具备数据库级幂等。
- [ ] 跨服务一致性明确选择 Outbox、Saga、TCC 或 XA。
- [ ] 事件支持重复、乱序、重放、死信和对账修复。
- [ ] 事实数据源、同步 SLA 和人工介入状态明确。
- [ ] API 与事件契约向后兼容并有 Contract Test。
- [ ] 日志、指标、Trace 和业务 SLO 覆盖完整链路。
- [ ] 灰度、优雅停机、故障演练和回滚流程可执行。

## 24. 学习路线

1. 从模块化单体理解领域边界和数据所有权。
2. 掌握服务发现、网关、配置和同步/异步通信。
3. 掌握超时、重试、熔断、隔离、限流和幂等。
4. 理解 CAP、最终一致性和重复/乱序问题。
5. 实践 Transactional Outbox、Saga 和 TCC。
6. 建设 Contract Test、可观测性、对账和故障恢复。
7. 通过故障注入验证部分失败下的系统行为。
