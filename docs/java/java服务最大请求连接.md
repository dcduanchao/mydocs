# Java 高并发：65535 个端口、TCP 连接与百万级请求原理

> 适用场景：Linux 服务器部署 Spring Boot / Java 应用，理解端口、TCP 连接、并发请求、QPS 及 NIO/epoll。

## 一、核心结论

一台服务器的端口号最大为 **65535**，但这**不代表最多只能接受 65535 个请求或 TCP 连接**。

需要区分四个概念：

- **端口**：用于定位服务器上的网络服务，如 `8080`。
- **TCP 连接**：由源 IP、源端口、目标 IP、目标端口构成的**四元组**标识。
- **并发请求数**：同一时刻正在处理的请求数量。
- **QPS**：每秒完成的请求数（具体统计口径需要统一）。

一台服务器可以使用同一个监听端口维持大量 TCP 连接；一条 TCP 连接也可以承载多次 HTTP 请求。

## 二、为什么 8080 端口可以支持大量客户端？

假设 Spring Boot 应用启动于：

```bash
java -jar app.jar
```

```yaml
server:
  port: 8080
```

服务器地址：`192.168.1.100:8080`。

多个客户端可以同时访问同一端口：

```text
客户端 A：10.0.0.1:50001 ──┐
客户端 B：10.0.0.2:50001 ──┤
客户端 C：10.0.0.3:50002 ──┼──> 服务器 192.168.1.100:8080
客户端 D：10.0.0.4:50003 ──┘       Spring Boot 应用
```

这些连接的服务器端口都为 `8080`，但四元组各不相同，因此操作系统可以区分。

### TCP 四元组

```text
(源 IP, 源端口, 目标 IP, 目标端口)
```

| 源 IP | 源端口 | 目标 IP | 目标端口 |
|---|---:|---|---:|
| 10.0.0.1 | 50001 | 192.168.1.100 | 8080 |
| 10.0.0.2 | 50001 | 192.168.1.100 | 8080 |
| 10.0.0.3 | 50002 | 192.168.1.100 | 8080 |
| 10.0.0.4 | 50003 | 192.168.1.100 | 8080 |

**边界情况：**如果源 IP、目标 IP 和目标端口都固定，单个源 IP 可用源端口数量会限制同一组地址之间可同时建立的连接数。但不同客户端 IP 的连接不受同一份源端口空间限制。

## 三、百万请求不等于百万连接

| 指标 | 含义 | 示例 |
|---|---|---|
| TCP 连接数 | 同时维持的网络连接 | 100 万连接 |
| 并发请求数 | 同时正在处理的 HTTP 请求 | 1 万请求 |
| QPS | 每秒完成的请求数 | 10 万 QPS |
| TPS | 每秒完成的事务数 | 依事务定义而定 |

### QPS 和处理时延的关系

根据 Little 定律，在系统稳定、统计口径一致时：

```text
平均在途请求数 ≈ QPS × 平均请求响应时间（秒）

QPS ≈ 平均在途请求数 / 平均请求响应时间（秒）
```

例如平均有 1000 个请求在途，平均耗时为 `10 ms = 0.01 s`：

```text
QPS ≈ 1000 / 0.01 = 100000
```

即理论上可能达到 **10 万 QPS**。这只是数学关系，不意味着任意 Spring Boot 服务都能够达到这个性能；真实吞吐量受 CPU、线程池、数据库、锁竞争、网络等因素限制。

### HTTP 连接复用

- **HTTP/1.1 Keep-Alive**：一个 TCP 连接可以顺序承载多个请求。
- **HTTP/2 多路复用**：一个 TCP 连接中可以承载多个并发请求流。

因此，请求总数不受端口数量直接限制。

## 四、Java 如何管理大量 TCP 连接？

### 1. 阻塞式模型

在典型的“一个连接对应一个阻塞线程”设计中，大量连接可能意味着大量线程，造成：

- 线程栈内存占用；
- 上下文切换开销；
- 线程调度及系统资源压力。

需要注意：并不是所有阻塞 I/O 服务器都严格为每个连接永久分配一个线程，具体依赖服务器实现。

### 2. NIO + Linux epoll

NIO 的核心思路是让少量事件循环线程管理大量 Socket，并在连接**就绪**时处理对应事件。

```text
      大量 TCP 连接
            │
            ▼
       Linux epoll
    检测读/写就绪事件
            │
            ▼
   Java NIO Selector / Netty EventLoop
            │
            ▼
      网络数据收发
            │
            ▼
      业务处理逻辑
```

**关键区别：**百万连接不等于百万请求同时执行。`epoll` 提升的是 I/O 事件管理效率，不会消除 CPU、磁盘、数据库或阻塞业务逻辑的限制。

### 3. Spring Boot/Tomcat 的情况

Spring Boot 使用嵌入式 Tomcat 时，常见配置是 NIO 连接器：

- NIO 可以管理多个连接；
- 普通 Spring MVC 同步请求仍通常使用工作线程执行；
- 阻塞数据库调用、远程调用等仍可能占满工作线程。

Netty 的 EventLoop 也要求避免在事件循环线程中执行长时间阻塞操作。

## 五、单机百万连接的实际限制

| 限制因素 | 说明 |
|---|---|
| 文件描述符 | 连接 Socket 通常占用进程文件描述符 |
| 内存 | Socket、TCP 缓冲区、应用对象等占用内存 |
| CPU | TCP/TLS、序列化和业务计算需要 CPU |
| 带宽 | 决定数据传输能力 |
| 网络与内核配置 | 监听队列、缓冲区和内核资源限制等 |
| 应用架构 | 线程池、连接池、阻塞操作和 GC 等 |

Linux 常用排查命令：

```bash
# 查看当前 Shell 的文件描述符上限
ulimit -n

# 查看系统文件描述符上限
cat /proc/sys/fs/file-max

# 查看监听的 TCP 端口
ss -lnt

# 查看 TCP 连接状态统计
ss -s

# 查看 Java 进程（JDK 工具）
jps -l
```

> 注意：`ulimit -n` 显示的是当前 Shell 限制，不一定等于由 systemd 或其他进程管理器启动的 Java 进程限制。可通过 `/proc/<PID>/limits` 核对实际运行进程。

## 六、不同性能目标意味着什么？

### 100 万 TCP 长连接

单机有可能达到，尤其是在连接大部分时间空闲、资源与内核参数适当调整时。但依赖内存、文件描述符、业务协议与应用实现，不能单靠配置端口实现。

### 每秒 100 万 HTTP 请求

明显比维持 100 万条空闲连接更困难，需要很高的请求处理吞吐量。对于涉及数据库、事务或外部服务的接口，经常需要缓存、异步处理和多机扩展。

### 单机 Spring Boot 能达到多少 QPS？

**没有固定答案。**简单内存接口、复杂计算接口和数据库事务接口的 QPS 可能相差多个数量级，应通过压测确定吞吐量、平均与尾部延迟、错误率和资源利用率。

## 七、建议的动手实验

在 Linux 上部署一个 JDK 21 + Spring Boot 应用，逐步验证：

1. 使用 `ss -lnt` 确认应用只监听 `8080` 端口。
2. 构造大量 TCP 长连接，观察 `ss -s`、文件描述符数量、内存与 CPU。
3. 对简单接口执行 HTTP 压测，分别关注连接数、并发请求数和 QPS。
4. 增加数据库调用或模拟阻塞，观察 Tomcat 工作线程、连接池和尾延迟的变化。
5. 使用 Prometheus + Grafana 采集 JVM、请求延迟、吞吐量、GC 与主机指标。

建议在测试环境执行，逐步提高负载，避免压测影响生产服务。

## 八、总结

记住以下三个重点：

1. **TCP 连接通过四元组区分，多个连接可以共用服务器的 8080 监听端口。**
2. **QPS、并发请求数和请求耗时有关，连接数并不直接等于请求数。**
3. **NIO + epoll 能用较少线程高效管理大量网络连接，但业务处理能力仍受硬件和外部依赖限制。**

**一句话概括：65535 是端口号范围的限制，不是 Java 服务器接收请求数的上限。**
