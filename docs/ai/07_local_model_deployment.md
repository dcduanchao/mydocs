# 07 本地模型部署：Ollama 与 vLLM

## 1. 适用场景

本地模型适合隐私数据、稳定低成本吞吐、离线环境、定制模型和供应商备用。代价是 GPU、显存、模型下载、升级、推理优化和运维责任由团队承担。

```text
应用 -> Model Gateway -> vLLM/Ollama -> GPU
```

## 2. Ollama

Ollama 适合本地开发、Demo 和小规模内部服务：

```bash
ollama pull qwen2.5:7b
ollama run qwen2.5:7b
curl http://127.0.0.1:11434/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen2.5:7b","messages":[{"role":"user","content":"介绍 RAG"}],"stream":false}'
```

开发接口不能直接暴露公网。生产需要认证、网关、并发和 Token 限制，Ollama 的默认本地接口不等于安全服务。

## 3. vLLM

vLLM 面向 GPU 推理服务，通常提供 OpenAI 兼容 API：

```bash
vllm serve /models/qwen \
  --served-model-name qwen-local \
  --host 0.0.0.0 \
  --port 8000 \
  --max-model-len 32768
```

实际参数受 vLLM、模型架构和 GPU 影响。生产启动前验证张量并行、显存、量化、工具调用、流式和停止策略。

## 4. GPU 与显存

显存大致由以下构成：

```text
模型权重 + KV Cache + 激活/临时空间 + Runtime 开销
```

影响因素：参数量、精度（FP16/BF16/INT8/INT4）、上下文长度、并发和 Batch。提高最大上下文或并发会显著增加 KV Cache。

```bash
nvidia-smi
nvidia-smi dmon
```

显存余量过低会导致请求抖动、OOM 或频繁卸载。不能只按模型参数量估算机器规格。

## 5. 量化

量化降低权重精度和显存占用：

| 方式 | 特点 |
|---|---|
| FP16/BF16 | 质量和兼容性较好，显存较高。 |
| INT8 | 通常质量损失较小，需硬件/框架支持。 |
| INT4/GPTQ/AWQ | 显存低，推理速度和质量需实测。 |

量化模型需要用真实业务评估准确率、结构化输出、工具调用和长上下文，不能只看通用分数。

## 6. 模型服务参数

- 最大上下文和最大输出 Token。
- 并发请求和最大 Batch Token。
- GPU Memory Utilization。
- 张量并行/流水线并行。
- 量化格式和 KV Cache 精度。
- 流式、停止词、JSON Schema 和 Tool Calling。

参数越激进不一定吞吐越高，可能增加排队和 P99。通过固定并发阶梯压测吞吐、首 Token 和 P99。

## 7. 服务化

模型服务前放统一 Gateway：

- TLS、认证、租户和模型权限。
- 请求大小、Token、并发和费用上限。
- 健康检查区分进程存活和模型可用。
- 关闭时等待生成请求或取消。
- GPU、显存、队列和请求延迟监控。
- 模型文件校验、只读挂载和供应链扫描。

## 8. 多模型与热加载

一个 GPU 同时加载多个大模型会竞争显存和 KV Cache。按流量选择常驻模型、分时加载或独立 GPU 节点。模型热加载要有容量检查、请求排空和回滚，不要在高峰直接删除旧模型。

## 9. 数据与安全

- 模型权重来自可信仓库并校验 Hash。
- 镜像和依赖固定版本，禁止任意远程代码执行。
- 推理节点不挂载生产数据库凭据和宿主机 Docker Socket。
- 日志默认脱敏 Prompt、响应和文件内容。
- GPU 节点按租户、网络和数据等级隔离。

## 10. 本地与云模型路由

```text
敏感/离线 -> 本地模型
高复杂度 -> 云端大模型
低成本分类 -> 本地小模型
本地不可用 -> 经过合规审批的云端备用
```

本地模型也会产生运维成本和质量差异。路由配置需要 Capability Matrix 和评估基线。

## 11. 常见故障

### GPU OOM

降低并发、上下文、输出上限或量化精度，检查显存碎片和其他进程；不要只不断重启。

### 首 Token 很慢

检查模型加载、排队、Batch Token、Prompt 长度、GPU 利用率和 CPU Tokenizer。

### 吞吐低但 GPU 空闲

检查请求是否串行、CPU/网络瓶颈、Batch 配置、模型量化和客户端连接池。

### 输出质量下降

确认模型文件、量化版本、Tokenizer、Prompt、采样参数和上下文长度没有变化，用固定评估集回归。

## 12. 生产检查清单

- [ ] GPU、显存、模型精度、并发和上下文经过压测。
- [ ] 模型文件、镜像和依赖固定并校验。
- [ ] 推理 API 不直接暴露，经过认证、限流和网关。
- [ ] 监控 GPU、显存、队列、首 Token、P99 和 OOM。
- [ ] 模型升级、量化切换和回滚流程可执行。
- [ ] 本地与云模型的路由、合规和降级策略明确。
